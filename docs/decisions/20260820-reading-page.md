# 読解ページ（工房の2アプリを1本の流れに統合して演習室へ移す・第1弾）

## 背景

英語長文の読解訓練を、生徒が家で自分で回せる形にする。工房（quiz_generator）には ①文脈読解コーチ（`apps/reading-coach/`・1195行）②構文分析アプリ（`apps/構文分析アプリ/index.html`・701行）の2本があり、**論理構造の扱いが重複**していた。加えて読解コーチには**保存の仕組みが1つも無く、画面を閉じると入力が全部消える**（これが自習に出せない最大の穴）。

設計書: quiz_generator `docs/読解アプリ統合_設計書.md`（承認済み）／決定: DEC-039／作業指示書: 統合塾運営エージェント `docs/work-orders/2026-08-20-reading-app-build.md`。

塾長は 2026-08-20 に**第1弾のみ承認**。AI 講評をアプリの中で回す第2弾は**不承認**で、その下ごしらえ（呼び出し口の用意）も含まない。**追加費用0円を維持する。**

## 決定

1. **置き場所は演習室の1ページ**（`/reading`）。生徒の入口は既存の LINE 自動ログインに相乗りし、ID もパスワードも入力させない。DEC-037 が定めた「記録を持つ必要が出たら移管を検討する」という見直し条件に乗る形。

2. **タブをやめて1本の流れにする**（読む→切る→大意→組み立て→全体→まとめ）。構文は独立タブではなく「**困った1文だけ降りる**」白文表示として流れの中に埋め込む。構文分析アプリの論理構造タブは畳んだ（読解コーチ側の1本に寄せる）。練習3問は「**構文の素振り**」（`/reading/syntax`）として独立に残した。「問題を追加」タブは移していない（教材づくりは工房の仕事）。

3. **全文の構文自動採点は作らない**（第1弾の範囲外）。品詞と働きの正解を全語に付けて講師が検収する必要があり、いま止まっている正規形の検収に、もう一列の検収待ちを足すことになるため。降りた1文は「書き込み用の余白つき白文」を出すところまで。

4. **途中保存は「生徒 × 講」で1つの JSON**（`reading_progress` テーブル・`024_reading_progress.sql`）。どこで切ったか・大意・組み立て・ヒントを何段押したかが全部そこに入る。**講師の画面はこの JSON から集計する**（別に集計表を持たない）。学習エンジン（`card_states`/`review_logs`）には一切触れない純追加。

5. **保存は端末優先＋サーバー後追い**。開いた瞬間は端末の控え（localStorage）から復元し、同時にサーバーへ問い合わせて**更新時刻の新しいほうを採る**。古い端末が新しい作業を上書きしないよう、サーバー側でも時刻を比べて拒む。**置き場所が未適用のあいだは自動で「この端末にだけ保存」に切り替わる**（生徒の入力を失わない）。

6. **判定ロジックは画面から切り離して移植した**（`src/lib/reading/`）。工房の app.js の判定（必須切れ目の見逃しのみ指摘・切りすぎは減点しない・ex. と ← は相互許容・字下げから親を導く）をそのまま純関数にし、テストで固定した。届いている6講の実データに対する検査も含む（工房が形を変えたら赤くなる＝C22 の見張り）。

7. **正規形（AI採点の基準）が無くても完成する形にした**。検収済みの講にアンカーが入れば AI 講評の文章がそちらを基準に切り替わり、無ければ教材の模範を基準にする。**検収待ちで開発も利用も止まらない。**

8. **AI 講評は貼り付け方式のまま**。アプリは「講評をお願いする文章」を作るだけで、外部へは一切送らない（第2弾は不承認のため、呼び出し口も作らない）。

9. **組み立ての操作はドラッグではなくボタン**（↑↓で順番・→←で字下げ）。工房版はドラッグだったが、生徒の中心はスマホで取りこぼしが多いため。判定のしくみは同じ。

10. **教材データは端末の先読み（PWA）の対象から外す**（`next.config.mjs` の `publicExcludes`）。理由は2つ:
    - ログインが切れた状態で先読みすると、**教材の代わりにログイン画面がキャッシュに焼き付く**（見張りが未ログインをログイン画面へ回すため。実物で再現を確認）
    - 工房で教材を作り直したとき、古い内容が端末に残るのを避ける

11. **ログイン切れは専用のエラーとして扱う**。JSON を頼んだのに HTML（ログイン画面）が返る場合を、リダイレクト・中身・401 の3通りで見分け、「ログインし直してください」の画面に落とす。

## 影響

- 増える約束ごとは **C22（工房→演習室の教材データの受け渡し）のみ**。置き場所・ファイル名・`index.json` の形を変えると読解ページが教材を読めなくなる。C23（AI 呼び出しの相乗り）は第2弾のものなので今回は発生しない
- 下メニューは増やさない（生徒4項目の定員を守る）。入口はホームの導線と「もっと」から
- 講師の入口は `/students/progress` から `/students/reading` へ

## 直接の対話で決まったこと（ADR 20260820-direct-dialogue-for-ux-tuning）

この作業に限り、画面の使い勝手は塾長と直接やり取りしてよいことになっている。本セッションで作業側が決め、記録に残した判断は次のとおり（いずれも見た目・操作の範囲で、憲法には触れない）。

- 組み立てをドラッグからボタン操作に変えた（上記9）
- 段落タブで進み具合の違う段落へ移ったとき、その段落が到達している段階まで自動で戻す（切り終える前に組み立てを開くと空になり、行き止まりに見えるため）
- アプリのインストール案内を読解ページでは出さない（学習ページと同じ扱い。操作を隠していたため）
- 「まとめ」のスクリーンショット依頼をやめた（講師の画面に届くため不要）

## 代替案

- **添削室に載せる**: 提出物の器はあるが読解の途中経過を持つ形ではなく、器から作り直しになる。見送り
- **工房のままネットに公開**: 誰の答案か分からず講師が見られない。「生徒が自習で使う」を満たさない。見送り
- **ドラッグ操作を残す**: スマホでの取りこぼしが多く、生徒の主デバイスに合わない。見送り
