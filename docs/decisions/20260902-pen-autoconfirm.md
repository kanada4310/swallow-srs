# 全記号の自動確定への転換＋波線・タッチ修正・カッコ描画（実機確認の第2陣・5件）

## 背景

指示書 2026-09-02-srs-pen-autoconfirm（旧指示書 2026-09-02-srs-pen-ux2 を置き換え）。
塾長の実機の使用感に基づく**方針転換**（2026-09-02 承認・検討会 2026-08-31 の一部を上書き）:
「確信が足りなければ確定せず候補選びに回す」をやめ、**候補が割れる場面でも最上位候補を
自動で確定・表示し、候補欄はなるべく出さない。誤りはあとからタッチで直す**。
合格水準の「取り違え0.5%以下」は「**修正されないまま採点まで残った誤り**」と読み替える。

## 決めたこと

### 1. 全記号の自動確定（候補欄の原則廃止）

- `PenSyntaxAnnotator` と計測ページの確定の入口で、判別の best（最有力候補）が
  あれば ambiguous でもその場で確定・表示する。候補チップを出すのは
  **best を立てられない（拾えず）ときだけ**（従来の見せ方への逃げ道として残す）
- **蓄積の関所の見直し（実装者判断・第2層）**: 迷いのある確定
  （ambiguous＝確信の下限未満・候補の差が小さい・お手本と意見割れ）の線は
  **実書き蓄積に入れない**。着手前に蓄積されていた線と同じ範囲だけが蓄積される
  （＝お手本の純度は転換前と同一に保つ）。
  **タッチで訂正された線も蓄積に採らない**（訂正後の値の見本として採る案は不採用）。
  理由: 訂正には「判別の訂正」と「分析の考え直し」の2種類があり画面から区別できない。
  後者を採ると誤ラベルのお手本が混ざる。関所は「誤ったお手本を入れない」を最優先する
- 「一手戻す」＝末尾1件の対応関係を保つため、蓄積しない反映にも skip 印付きの
  場所取り行を積む（従来は蓄積されない反映の後の取り消しが1つ前の正しい線を消していた）
- 計測（metrics.ts）に確定のしかた 'chips'（着手前）/'auto'（転換後）の2つの読みを持たせ、
  着手前との比較可能性を保つ。合成データでの自動確定の読み:
  標準の書き手 一発確定96.1%・要修正3.9% ／ 癖のある閉じ括弧 63.3%・36.7%（実機の実測ではない）

### 2. 波線の筆順登録昇格とひとつながり描画

- 波線を必須のお手本へ昇格（**推奨どおり必須**。括弧8種＋働き7種＋波線＝16種）。
  登録済みの利用者には `missingRequired` の続き再開の仕組みそのままで
  **波線1種だけの追加登録**が自動で出る（専用の入口は作らない＝仕組みが1つで済む）
- 描画を単語ごとの文字飾り（CSS）から、下線と同じ**連結線分＋波形のSVG**へ
  （行ごとに1本・単語の間で切れない）。行またぎの連結も下線と同じ扱い
  （波線には働きの欄が無いため、下線の3条件のうち「働き未記入」を除く2条件）

### 3. 下線のタッチ修正

- 下線・波線をタッチすると修正メニュー（**下線↔波線の種類の変更・削除**）。
  当たり判定は表示と同じ連結線分から出す純関数 `findLineAt`（下線と波線が
  重なるときは波線を優先＝誤って下線と判定された波線を直すのが主目的）
- **まとまり（範囲）の変更は含めない**（実装者判断）: 削除して書き直すほうが速く、
  範囲指定のタッチ操作を足すと画面が複雑になるため
- 種類の変更も訂正なので、その線は蓄積から外す（採り直さない。理由は1と同じ）

### 4. 働きのタッチの2分岐

- 働きのマスのタッチ→「**修正**（値の変更・削除）」と「**印の追加**（仮・真・強）」の
  2分岐を先に出す。同格の「同」は働きの値なので修正の一覧のまま。
  拾えなかった線の「一覧から選ぶ」は分岐を飛ばして一覧を直接開く（入力し直しのため）

### 5. 重なるカッコの描画の乱れ（描画の問題・吸着に誤りなし）

- 再現文 The girl ⟨standing (by the door)⟩ is my sister. で切り分けた結果、
  **原因は描画**（吸着は ) ⟩ とも正しく door の後ろに付いていた）。2つの相乗り:
  1. **フォントの字面の食い違い**: 日本語フォント（Hiragino Sans / Yu Gothic UI）の
     丸括弧は字面が大きく基線より下にぶら下がる設計。⟨ ⟩（U+27E8/E9）は日本語フォントに
     無く別フォントへ落ちて小さく中央寄りに描かれる。2026-08-28 の半角そろえ
     （20260828-symbol-halfwidth）は「どの字を使うか」だけをそろえ、フォントごとの
     字面の違いまでは吸収できていなかった（＝指示書の言う「漏れた経路」）
  2. その食い違いの上に意図した縦ずらし8px（20260831）が乗り、段差が大きく見えた
- 対処: 括弧の重ね描きを**自前のSVG字形**へ（`bracketGlyphPath`・8×20pxの同じ箱・
  4種とも同じ上下端・閉じは左右反転）。端末のフォントによらず大きさ・基線が完全に
  そろい、重なりの段差は意図した8pxちょうどになる。縦ずらし8px自体は据え置き
  （そろった字形なら8pxで読み分けられることを前後スクリーンショットで確認）

## やらないこと

- 認識エンジンの照合方式・採点ロジック・4色の色分めの変更（スコープ外）
- 保留列（heldChips）と候補チップの仕組みの撤去（拾えずの逃げ道として残す）

## 影響範囲

ペン入力の2画面（構文の練習・ペン判別の計測）専用の部品のみ。
共有部品 SyntaxAnnotator・採点・データベースの形は不変。
