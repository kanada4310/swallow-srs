# 候補が出ている最中でも書き始めを受け付ける（線を失わない）

## 背景

同日の改修（ADR `20260827-pen-commit-latency`）で、記号の確定が
「隣の単語に書き始めた瞬間」まで早まった。その副作用として、**判別に迷ったときの
候補（チップ）が、書いている最中に出る**ようになった（従来は次の画を書き終えてから）。

ところが候補が出ている間は、書き込みの受付そのものが止まる作りだった
（`PenSyntaxAnnotator` の `active: !disabled && !chips`、計測ページも同様）。
候補を消す経路は「候補を選ぶ／取り消す」の1つだけで、**書き続けて消える経路は無い**。

そのためテンポよく書くと、**次の記号の1画目が黙って消える**。
実際、修正前のテストでは接触の記録が1件も残らなかった（＝線が消えたことすら
記録に出ない）。これは 2026-08-26 に塾長が報告した「**ペンが反応しなくなる**」と
同じ体験であり、速く書けるようにした改修が速く書いたときに線を失わせることになる。
本番反映の前に解消する（指示書 2026-08-27-srs-pen-chip-interrupt）。

## 決定

### 1. 書き始めたら候補は黙って引っ込め、その1画目から描く

候補が出ている状態で新しい筆画が始まったら、候補を閉じ、**その接触をそのまま線にする**。
閉じた候補は「選ばれなかった」＝取り消し（✕）と同じ扱いにし、その線は破棄する。

受付を止めない（`active: !disabled`）ことが要点で、止めたままだと
「閉じてから描き直す」しかなくなり、1画目を失う問題が残る。

### 2. 「候補を押す操作」と「書き始め」は当たり判定で分ける

候補の枠はキャンバス（`z-10`）より上（`z-20`）に重ねてあるため、
**候補を押した接触はキャンバスに届かない**。キャンバスの `onPointerDown` に届くのは
候補の枠の外に触れたときだけである。つまり両者は座標で自然に分かれており、
時間や距離のしきい値を新設する必要がない（新しいしきい値は端末ごとに破綻する）。

採らなかった案:
- 「押した直後○ミリ秒は書き始めとみなさない」— しきい値の当たり外れが端末で変わる
- 「候補を画面の隅に固定して重ならないようにする」— 書いた線から離れて視線が飛ぶ
  （候補の見た目・並び順の変更は指示書のスコープ外でもある）

### 3. 候補の枠の外を軽くタップしたときは、候補を閉じるだけ

キャンバス上の軽いタップは、ふだんは品詞・働きの一覧を開く操作である。
候補が出ているときにこれをそのまま通すと、閉じると同時に一覧まで開いて驚かせる。
**その接触で候補を閉じた場合だけ**、一覧は開かず閉じるだけにする
（「枠の外をタップして閉じる」という一般的な作法に合わせる）。

### 4. 計測ページ（pen-lab）にも同じ扱いを入れる。ただし数字は数えない

同じ症状が計測ページにもあり、塾長が実測を取る場所なので放置できない。
ただし計測の数字は歪めない: **書いて閉じた線は「拾えず」にも「救済」にも数えない**
（書いたつもりの記号を答えてもらっていないので、判定材料がない）。お題は据え置きで、
同じお題をもう一度書き直せる。画面には「前の線は捨てました（数えていません）」と出す。

### 5. 閉じたことは「入力の記録」に残す

実機で症状が出たときに経緯を追えるよう、閉じた事実を記録に1行残す
（`kind: 'note'`）。外部送信はしない（端末内のみ）。

## 根拠・確かめたこと

- 自動テスト3件を新設（この経路には従来テストが無かった）:
  ①候補が出ている最中に書き始めても受け付けられ、候補は引っ込む
  ②候補を押す操作は従来どおり効く ③枠の外の軽いタップは閉じるだけ。
  ①③はいずれも**修正前のコードでは失敗する**ことを確認済み（テストが症状を捉えている）
- 開発サーバーの実ブラウザ（Playwright・iPad Mini 相当・テスト生徒・マウスで書く設定）で
  「構文の練習」「ペン判別の計測」の両方を実測。候補が出た状態で書き始めた接触が
  `受理(mouse)` として記録され、続いて確定まで進むことを記録の実物で確認した

## 影響しないもの

判別の精度・記号の見分け方・候補の見た目と並び順・0.75秒の待ち時間・
ゾーン方式と手のひら対策・記号台帳・タップ方式の共有部品（`SyntaxAnnotator`）。
DB 変更なし・外部送信なし・費用なし。
