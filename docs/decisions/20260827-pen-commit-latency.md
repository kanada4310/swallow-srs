# 続けて書いた記号が1つにまとまる問題の解消（境界で即確定・まとめ判定の一本化）

## 背景

塾長の実機フィードバック（2026-08-27）:

> 書き込んでから読み取られて描画されるまでの間、すべてが1つの記号として認識されてしまう。
> 紙に書くのと同じ感覚でどんどん書き込んでいきたいが、少し判定に時間がかかるためストレスがある。

ペン方式を選ぶ理由は「紙と同じ感覚で書けること」なので、書く速さについてこられない
ことは機能の存在意義に関わる。原因は2つの仕組みの重なりだった（指示書
2026-08-27-srs-pen-commit-latency で秘書が特定し、実装側でも裏取りした）。

1. **確定が「最後の一画から 0.75 秒静止するまで」先送りされていた**
   （`GROUP_WAIT_MS`。書き込み部品と計測ページに同じ値が複製）
2. **いったん広がったまとまりが、以降の書き込みを吸い込んだ**。
   まとめ判定 `shouldGroupStrokes` の場所の比較相手が「まとまりに入っている
   **全画の外接箱**」だったため、一度横に広い箱ができると、その内側に入る画は
   距離ゼロ扱いになり 40px のしきい値を素通りした。単語の間隔は12px程度なので、
   隣の単語にテンポよく書くだけでこの経路に入る

線そのものの描画は即時で、遅いのは「記号として確定するまで」だった。

## 決定

### 1. 触れた瞬間に境界をまたいでいれば、待たずに確定する

ペンが触れた瞬間（`onStrokeStart`）に、直前のまとまりと**行・段（品詞/本文/働き）・
単語**がちがうと分かれば、0.75秒を待たずにその場で確定する（`useStrokeGrouping`）。
1点しか分からない時点の判定なので、**確信のある根拠だけで切る**:

- 括弧は本文の上端より少し上から書き始めるため、段の判定は余裕（行の背丈の3割）を
  取り、際どい位置は「どちらとも言えない」として切らない（書き終えた時点で判定し直す）
- 同じ単語の同じ段で書き続けている間は、**いままでどおり待つ**
  （○で囲んだ漢字・2画で書く S や V・括弧の書き直しを途中で切らないため）

### 2. 場所の比較相手を「直前の1画」に変え、画面の構造で切る根拠を数える

`src/lib/pen-syntax/grouping.ts`（新設・純関数）に集約。上から順に見て、
当てはまったら別の記号として切る:

| 順 | 根拠 | 内容 |
|---|---|---|
| 1 | 間があいた | 0.9秒以上 |
| 2 | 行がちがう | 折り返した別の行（`groupLines`/`pickLine`） |
| 3 | 段がちがう | 品詞（上）・本文・働き（下）（`laneOf`） |
| 4 | 横長の線 | 下線・波線は1画で完結。続きの画を足さない |
| 5 | 単語をまたいだ | 本文の帯に重なる線（括弧）が単語の中心をはさんだ |
| 6 | 単語がちがう | 付き先の単語（`snapNearestToken`）がちがう |
| 7 | 大きすぎる | まとまり全体が「記号1つ」としてありえない大きさ |
| 8 | 離れている | 直前の画から40pxより遠い |

「直前の画のすぐそば（12px以内）」なら 6・8 は見ない（複数画の文字を切らないため）。
ただし**本文の帯に重なる記号（括弧）は、近くても付き先の単語がちがえば切る**
（`…）` と `［…` が語間で隣り合う場合に必要）。

**他の案を採らなかった理由**（指示書が実装者判断とした点）:

- 直近の数画の外接箱で比べる案: 画数の多い記号ほど箱が広がるという性質が残り、
  ○で囲んだ漢字を書いたあとに同じ問題が再発する
- 距離のしきい値を小さくするだけの案: 単語の幅・字の大きさ・画面の幅で
  適正値が変わり、端末ごとに破綻する。**画面の構造（単語の箱・段）で切る**ほうが
  寸法に依存しない
- 待ち時間だけを短くする案: 画数の多い記号（○で囲んだ漢字は6〜10画）が
  途中で切れる。指示書の禁止事項でもある

### 3. 待ち時間 0.75 秒は変えない

境界での即確定が入ったことで、待ち時間が効くのは「**書く手を止めたとき**」だけに
なった。合成データの計測でも、続けて書く限り待ち時間は体験に出てこない。
一方で短縮すると画数の多い記号を切る危険があるため、**据え置く**（第2層判断）。
実機の実測を見て、必要なら次の便で調整する。

### 4. まとめ判定・待ち時間・確定の呼び出しを1か所に集約

書き込み部品（`PenSyntaxAnnotator`）と計測ページ（`pen-lab`）に複製されていた
判定・タイマー・確定処理を `useStrokeGrouping` に一本化した
（2026-08-26 に入力処理を `useStrokeCanvas` へ一本化したのと同じ考え方）。
あわせて `useStrokeCanvas` の `onStrokeStart` が**書き始めの点**を渡すようにした。

### 5. 速さを測れるようにした（今回が初めて）

これまでの計測は判別の正誤だけで、**速さは一度も測っていなかった**。

- **実機**: 確定するたびに「入力の記録」へ `確定 N画 …（理由） 最後の一画から=◯ms
  次を書き始めてから=◯ms` を残す。計測ページに「確定までの時間（速さの計測）」欄を新設
- **合成データ**: `simulateCommits`（入力の時刻から確定の時刻を求める模擬計算）で
  新旧を比べる。旧方式の判定も比較用に `legacyShouldGroupStrokes` として残した
- **再生テスト**: 入力の記録から線と単語の箱を組み立て直す `replayGrouping` を追加し、
  症状の記録 `replays/2026-08-27-fast-writing-merge.json` を収録

## 計測（合成データ・実機の実測ではない）

`src/lib/pen-syntax/grouping.test.ts`（種固定）。

| 見るもの | 新方式 | 旧方式 |
|---|---|---|
| まとまりの一致率（書いた記号どおりに分かれたか・n=60回） | **100.0%** | 58.1% |
| 次を書き始めてから前が確定するまで（11記号を続けて書く） | **平均 0ms・最大 0ms** | 平均 140ms・最大 140ms |
| 書き終えてからその記号が形になるまで | **平均 268ms**・最大 750ms | 平均 494ms・最大 750ms |
| 11記号を書いたときに確定したまとまりの数 | **11** | 8 |

**判別の精度は測り直していない**（今回の変更は「どの画を1つの記号にまとめるか」だけで、
判別器そのものには触れていない）。既存の判別の計測は全件そのまま通っている。

開発サーバーの実ブラウザ（Playwright・iPad Mini 相当・テスト生徒）でも確認した:
隣の単語に書き始めた瞬間に前の記号が確定し、記録は
`確定 1画 次の記号に入った瞬間(単語がちがう) 最後の一画から=183ms 次を書き始めてから=1ms`。

## 影響

- ペン方式の書き込み全般（構文の練習・計測ページ）。タップ方式・共有部品
  `SyntaxAnnotator` には触れていない
- 判別器・吸着・反映・画面ガード（ゾーン方式）・記号の台帳は不変
- 待ち時間の途中で次を書き始めたとき、判別に迷った記号の候補チップが
  **書いている最中に出る**ようになった（従来は次の画を書き終えてから）。
  候補チップが出ている間に新しい線を受け付けないのは従来どおり

## やり残し

- 実機（タブレット＋ペン）での速さの実測は塾長の確認待ち
  （計測ページの「確定までの時間」欄で数字が出る）
- 書き終えた直後に「採点する」を押すと、最後の記号が待ち時間に間に合わないことがある
  （従来どおり・今回の変更で悪化はしていない）
